# Contributing

## Versioning

This project follows [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`.

- **MAJOR** — a change that breaks the public API (anything exported from `sveltekit-admin`,
  documented config shapes, or documented behavior a consumer could reasonably depend on).
- **MINOR** — a new, backwards-compatible capability.
- **PATCH** — a bug fix, performance improvement, or internal change with no effect on the
  public API.

While the package is `0.x.y`, a MINOR bump may still include a breaking change — that's what
`0.x` signals under SemVer. The plan is to cut `1.0.0` once the exported API (handler factory,
config shape, adapter interfaces) is considered stable, and apply the rule strictly from then on.

### Adding a changeset

Version bumps and CHANGELOG.md are generated by [Changesets](https://github.com/changesets/changesets),
not decided by hand at release time. Every PR that changes published behavior needs a changeset file
with a tagged frontmatter and summary.

#### Format

Each `.changeset/*.md` file has a frontmatter declaring the package and bump, and a body opening
with a tag:

```md
---
'sveltekit-admin': minor
---

feat: **Column sorting in list views.** Every column heading is a link; `?sort=` and `&dir=` live in the URL and compose with the active search and filters.
```

Name the file in kebab-case after the change (e.g. `widen-search-heuristic.md`), not via the
interactive CLI. You are writing it by hand so the name reflects the change in `git blame`.

#### Tags and bumps

The body opens with exactly one tag, lowercase, followed by a space or tab. The tag decides the bump type
and the changelog section the bullet lands in — it must agree with the frontmatter, or the linter
catches a drift before it ships:

| Tag | Bump | Use when the change |
|---|---|---|
| `breaking:` | `major` | forces existing callers to react |
| `feat:` | `minor` | gives a new lever or a new surface |
| `improvement:` | `patch` | refines something that already worked |
| `fix:` | `patch` | repairs something that was wrong |

#### Length and structure

- **300 characters** of summary (tag excluded, soft wraps counted as one space, markdown markup
  included). **600** for `breaking:`, which owes both what breaks and what to do about it.
- **One paragraph.** No blank line, no markdown heading, no fenced block; inline backticks are welcome.

Run `pnpm run lint:changesets` before pushing. It checks the tag, tag/bump agreement, the character
cap and the single-paragraph rule. CI runs it in the `changeset-check` job — a PR fails if any
changeset violates these rules.

#### The PR description matters

The engineering reasoning (why one atomic change instead of a loop, which regex was wrong, what race
condition existed) goes in the **PR description**, not in the changeset. The changeset answers
"what can I do now that I couldn't before"; that reasoning belongs in the diff's context, where the
next person meets it while reviewing or debugging.

#### Empty changesets

A PR that only changes tests, CI, docs, or internal dev tooling still needs a `.changeset/*.md`
file — an **empty** one, with no tag and no length cap:

```md
---
---

Docs only — nothing published changes. <what this PR does>
```

The reason is mechanical: the `changeset-check` job runs `changeset status --since=origin/main`,
and that command reports the package as changed for *any* modified file, not only published ones.
A docs-only or test-only PR with no changeset file fails CI exactly like a source PR would.

#### Versioning locally

`pnpm run version-packages` needs the `GITHUB_TOKEN` environment variable set — it resolves
each changeset's commit through the GitHub API. A local run requires
`GITHUB_TOKEN=$(gh auth token) pnpm run version-packages`. CI needs nothing — 
`.github/workflows/release.yml` already sets `GITHUB_TOKEN` at the step level. Versioning is
CI-only by design.

### Releasing

Nothing manual: merging to `main` runs the `Release` GitHub Action, which opens/updates a
"Version Packages" PR aggregating all pending changesets. Merging that PR bumps `package.json`,
regenerates `CHANGELOG.md`, tags the release, and publishes to npm.
